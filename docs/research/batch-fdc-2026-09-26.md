# Does the FDC see XRPL Batch? (2026-09-26)

**Short answer: yes, by the verifier's own code path and by an emulation on a real Batch.** This closes the open question in SPEC §6.10 and §10 ("XLS-56 Batch may be invisible to the FDC") as far as it can be closed before the testnet that Flare's verifier indexes enables `BatchV1_1`. **The one remaining step is a live attestation**, which costs one request once that happens.

## Why it matters now

- **Mainnet date.** On XRPL mainnet, `BatchV1_1` has held a majority since **2026-09-25 14:46:02 UTC** (`feature` via xrplcluster.com, `majority` 843662762 in the Ripple epoch). The earliest activation is therefore **2026-10-09 around 14:46 UTC**. On the testnet it is supported but not enabled.
- **What is at stake.** In a Batch the XRP leaves the account in **inner** transactions. Each inner transaction has its own hash, `Fee` 0, no signature, and `meta.ParentBatchID`. The outer transaction pays only the fee. If the FDC could not attest the inner transactions, an agent could move XRP out through a Batch without a provable deed. That would be a hole in §6.10 and in SUMMA's XRPL rail.

## The code path, read end to end

1. **Indexer:** `flare-foundation/verifier-xrp-indexer` @ `584695e` (2026-09-04).
   - `GetBlockResult` calls `ledger` with `transactions: true, expand: true`, and stores **every** transaction in the ledger's list.
   - What it stores: the hash, `Account`, the result from `metaData.TransactionResult`, and `sourceAddressesRoot`, which is computed purely from `AffectedNodes` balance decreases.
   - It never filters on signature, fee, flags or type.
2. **API:** `flare-foundation/verifier-indexer-api` @ `cb14a1f` (2026-09-22).
   - `getConfirmedTransaction(txId)` reads the stored JSON.
   - `xrp-entity-definitions.responseJson()` reshapes it into `{result: {…tx, meta: metaData, validated: true}}`.
   - `new XrpTransaction(…).balanceDecreasingSummary(sourceAddressIndicator)` is then called.
3. **MCC:** `@flarenetwork/mcc` 4.5.0, the exact version the API pins.
   - `spentAmounts` walks `meta.AffectedNodes`: every `AccountRoot` whose `Balance` fell, and by how much.
   - Again, no signature, fee, flag or type check.

## The emulation (XRPL devnet, where `BatchV1_1` is enabled)

The run used `tools/xrpl_testnet.py batch` to send a `tfAllOrNothing` Batch of two Payments, 3 and 2 XRP, from account `rpAJtifPip36NoKKKN6FHdrqY2SgkBcntG`:

| tx | type | Fee | signature | result | `ParentBatchID` | MCC `balanceDecreasingSummary(agent)` |
|---|---|---|---|---|---|---|
| `C0E4362D…1EED00` (outer) | Batch | 4 | yes | tesSUCCESS | — | success, **4** drops |
| `65B1F50C…0BC950` (inner) | Payment | 0 | no | tesSUCCESS | outer | success, **2 000 000** |
| `28AC92CE…458A17` (inner) | Payment | 0 | no | tesSUCCESS | outer | success, **3 000 000** |

- **The ledger call.** `ledger 5613336` with `transactions: true, expand: true` is the indexer's call. It returns all three transactions with their own hashes and full `metaData`.
- **The verifier logic.** Reshaped as the API reshapes them and passed to MCC 4.5.0, every drop that left the account is attributable to a transaction id the verifier would index: 5 000 004 in total.
- **Reproduce it:** `/tmp/mccrun/emulate.js` in the session. The script is 20 lines; the steps are above.

## What this changes

- **§6.10 and SUMMA's XRPL rail:** a Batch is an ordinary set of deeds. The outer transaction carries the fee and each inner transaction carries its amount. A watcher files all of them, and the docket counts the sum.
- **Discovery:** inner transactions are listed by `account_tx`, and they sit in the `AccountRoot` `PreviousTxnID` chain the sentinel walks. The sentinel therefore finds them through the verifier's own index.
- **Lancea:** the guard co-signs only `Payment`, so a `Batch` from the guarded account is refused, and prevention holds. It must also never sign a `BatchSigners` entry. It does not today, because it signs only the Payments it decodes.

## Caveats (stated, not waved away)

- This is not a live attestation. The testnet the FDC indexes does not have Batch yet.
- The deployed verifier may run a different build than the repository's `main`. Both repositories were read at the commits named above.
- If Flare's indexer points at a Clio server rather than rippled, `ledger` with `expand` is assumed to behave the same way. That was not checked.
